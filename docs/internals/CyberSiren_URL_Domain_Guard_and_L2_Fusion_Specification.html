CYBERSIREN — URL DOMAIN GUARD & L2 FUSION SPECIFICATION

Document: URL-L2-SPEC-v2.0 Date: 2026-06-14 (v2.0: v3 model update; original v1.0: 2026-05-19) Scope: SVC-03 URL Analysis — Domain Guard fast-path + L2 fusion sidecar (fusion_export/) Classification: Internal / Graduation Project
Context: This document specifies the two phishing-detection layers added to SVC-03 in PR #140 — the Go-side Domain Guard fast-path and the Python L2 fusion sidecar (fusion_export/scripts/serve.py, port 8765). Together they sit on either side of the existing L1 XGBoost URL model (see the companion CyberSiren_URL_Low_latency_Model_Specification.html). The deployed runtime pipeline as of commit 4c8b112 is Guard → L1 → TI → L2 Fusion. Layer 2 fuses two probabilistic signals (url_p from a char-LR URL model and op_p from a Histogram-Gradient-Boosting model over live enrichment features) into a single deploy_p with asymmetric, zone-based weighting.
Quick facts: Guard top-10K size: 10,000 entries (Cisco Umbrella)  |  Typosquat distance: Levenshtein d=1  |  Brand list: 20 hand-curated entries  |  Sidecar host:port: http://fusion-sidecar:8765 (compose) / 127.0.0.1:8765 (local)  |  Decision threshold over deploy_p: 0.50 (env CYBERSIREN_PHISHING__THRESHOLD)  |  Cache: TTL 5 min, 10,000-entry LRU keyed on the full URL.

1. Literature Foundation

The two new layers draw on five distinct strands of literature. Citations are minimal but each design decision in §3–§6 traces back to one of them.

Ref Source Used For
[A] Cisco Umbrella Popularity List (umbrella-static). Daily ranking of the most-queried domains on Cisco's recursive resolvers. Allowlist source for the Domain Guard top-10K fast path (§3.1). Chosen over Tranco/Majestic for query-volume coverage of end-user traffic.
[B] Levenshtein, V. I. (1966). Binary codes capable of correcting deletions, insertions, and reversals. Soviet Physics Doklady, 10(8), 707–710. Edit-distance metric for typosquat detection (§3.2). d=1 (rather than d≥2) keeps false-positive rate against 10K references negligible — see §10.
[C] Edelman, B. (2003) — brand impersonation in domain names; OECD & APWG industry reports on subdomain-based brand abuse. Justification for the brand-in-subdomain scan (§3.3). The pattern <brand>.<attacker-apex> remains one of the most common phishing primitives.
[D] Platt, J. C. (1999). Probabilistic outputs for support vector machines and comparisons to regularized likelihood methods. In Advances in Large Margin Classifiers. Motivation for requiring that url_p be a calibrated probability (rather than an uncalibrated score) so it can be linearly combined with op_p at fusion time (§6). In practice url_p is produced by LogisticRegression, which outputs a sigmoid probability natively; no separate Platt-scaling step is applied.
[E] Friedman, J. H. (2001). Greedy function approximation: A gradient boosting machine. Annals of Statistics, 29(5). Ke et al. (2017) — LightGBM. sklearn's HistGradientBoostingClassifier documentation. Choice of gradient-boosted trees over tabular operational features for op_p (§5). HGB handles mixed-type, missing-value-tolerant features without manual encoding.

Source: services/svc-03-url-analysis/internal/url/domainguard.go. Three independent signals, evaluated in this order:

3.2 Levenshtein-d=1 Typosquat Detection

Implemented in CheckDomain. For an apex d that misses the allowlist, the guard scans the 10K reference set for any entry within Levenshtein distance 1. Length-gap short-circuit: candidates whose length differs from d by more than one are skipped before the edit-distance computation runs.

AspectValue
Distance metricLevenshtein (insertion, deletion, substitution; no transposition cost — Damerau variant not used to keep the implementation single-pass)
Thresholdd = 1 only. See §10 for the rationale and the d=2 FP-rate analysis.
Short-circuitabs(len(candidate) - len(d)) > 1 → skip without running the DP table.
Latency (i7-10750H)~51 µs worst-case (BenchmarkCheckDomain_TyposquatDetect) — iterates all 10K references in the worst case.
Outcome on hitShort-circuit: guard_hit = "typosquat:<brand>" where <brand> is the matched reference apex. Verdict = phishing.

3.3 Brand-in-Subdomain Scan

Implemented in CheckSubdomainBrand. Walks the URL's labels left-to-right; if any non-apex label contains a known brand substring (with len(label) ≥ 4 as an FP gate), short-circuits as phishing.

AspectValue
Brand list20 hand-curated brands in brandSubstrings: paypal, microsoft, google, amazon, apple, facebook, instagram, netflix, github, linkedin, outlook, icloud, youtube, whatsapp, chase, wellsfargo, citibank, dropbox, discord, spotify.
FP gatelen(label) ≥ 4 — prevents matches against ultra-short labels where substring overlap is incidental.
Latency (i7-10750H)~157 ns per URL (BenchmarkCheckSubdomainBrand_Hit).
Outcome on hitShort-circuit: guard_hit = "brand-in-subdomain:<brand>". Verdict = phishing.

3.4 Apex extraction

The guard never operates on the raw URL string directly. ApexFromURL uses the Public Suffix List (PSL) via golang.org/x/net/publicsuffix to derive the apex (the eTLD+1) before any of the three stages run. Misformed URLs propagate as guard_hit = "" and fall through to L1.

4. Char-LR URL Model (url_p)

Source: fusion_export/fusion_kit/scoring.py:score_url_hash. A char-n-gram hashing pipeline feeding a logistic-regression classifier with calibrated outputs. Designed to be insensitive to TLD churn and resilient to lookalike Unicode by normalizing inputs to ASCII-lowercase before tokenization.

AspectValue
TokenizerChar n-grams over normalized URL string (scheme + host + path + query), n in [2, 4]. HashingVectorizer with 218 buckets — no fitted vocabulary, so the model is stateless across data drift.
NormalizationASCII lowercase; percent-decoded path; punycode-decoded host. Implementation: fusion_export/fusion_kit/url_normalize.py.
Classifiersklearn.linear_model.LogisticRegression with L2 regularization. C=2.0, ngram [2,4], 218 hash buckets (url_char_lr.metrics.json); class_weight='balanced', solver='liblinear', max_iter=3000 (fusion_export/scripts/train_url_model.py, build_pipeline()). Outputs a sigmoid probability directly — no separate calibration step is applied.
Artifactfusion_export/models/url_char_lr.joblib. Compressed joblib; load on sidecar start.
Metrics filefusion_export/models/url_char_lr.metrics.json. Stores: train_rows (304,181), augment_benign_rows, augment_benign_unique, augment_phish_rows, augment_phish_unique, train_roc_auc (0.9762, computed on training data), train_accuracy_at_0_5, n_features_bits, ngram_range, C. Does not store per-class FPR/FNR or PR-AUC.
InputsSingle string per URL.
OutputsOne float in [0, 1] per URL: P(phishing | URL string).

5. HGB Operational Model (op_p)

Models live infrastructure signals about a URL: who runs it, where it's hosted, what its TLS cert looks like, whether its hosting platform is known to be free / ephemeral.

HistGradientBoostingClassifier handles NaN natively by learning no split on a fully-missing column — these three features contribute zero discriminative signal in the current model. They will become active once live page-extraction enrichment is integrated.

5.2 Categorical handling for HGB

sklearn's HistGradientBoostingClassifier tolerates at most 255 distinct categories per categorical column. prepare_X_for_hgb handles this in two passes:

  • Columns with ≤ 255 distinct values in the training set are cast to pandas category dtype directly.
  • Columns over the limit (19 columns including asn_name, isp, cidr_block, cert_subject, registrar, etc.) are hashed via pd.util.hash_pandas_object and bucketed as abs(hash) % 4096, stored as float64. This produces 4,096 numeric buckets — not 255. The threshold of 255 governs which path is taken, not the size of the output bucket space.

5.3 Synthetic training injections

hgb_operational training includes two synthetic datasets injected by retrain_operational.py before fitting. These are load-bearing — without them the model produces incorrect results on common legitimate patterns.
  • 1,500 platform rows (500 benign brand-auth pages such as accounts.google.com; 500 benign developer deployments on vercel.app / github.io etc.; 500 phishing platform pages with subdomain_brand_count≥1 and fresh domains). Without these, is_ephemeral_platform=1 is treated as near-certain phishing and every legitimate Vercel/Netlify/GitHub Pages deployment is flagged. The synthetic rows teach the model to discriminate via subdomain_brand_count + title_brand_mismatch + domain_age_days.
  • 400 shortener rows (all benign: bit.ly, t.co, tinyurl.com, ow.ly, buff.ly). Real shortener URLs are absent from phishing feeds, so the model has no prior for them. The synthetic rows anchor the model on: old domain age + low cert age (90-day renewal) + trusted ASN + no login keyword = benign.

5.4 The is_ephemeral_platform feature

Operational hazard — duplicated suffix list. The set of ephemeral-platform suffixes is duplicated between fusion_export/fusion_kit/operational.py:_EPHEMERAL_PLATFORM_SUFFIXES (Python, used at training time and during sidecar re-enrichment) and internal/phishing/enricher/features.go:ephemeralPlatformSuffixes (Go, used by the /score-features fast path). The two lists must stay in sync — otherwise /score-features and /score can produce different verdicts for the same URL. Commit aa5dafd added 10 platforms (Wasmer, Replit .app / .co, repl.co, zya.me, dweb.link, ipfs.io, StackBlitz, CodeSandbox, CodePen). Whenever a suffix is added on one side, it must be added on the other.

Why it matters: hosting on a known free / preview / temporary-deployment platform (vercel.app, pages.dev, netlify.app, etc.) is a strong — though not overriding — phishing signal. The L2 fusion in §6 has a specific guard for legitimate platform deployments to avoid false-positiving them.

6. Fusion Math

Source: fusion_export/fusion_kit/scoring.py:fusion as of commit 4c8b112. The fusion function takes url_p (char-LR) and op_p (HGB operational), plus an optional shortener_mask, and returns deploy_p. Four zones plus a shortener override plus a high-op low-url_p guard. The math was rebalanced in aa5dafd and 4c8b112 after the original PR-#140 landed — what follows reflects current production behavior, not the historical version.

6.1 Boolean masks

NameDefinitionIntuition
in_cdnop_p < 0.01Operational signal is essentially absent — the host looks clean (typical CDN-fronted phishing).
in_high_opop_p > 0.60 AND url_p ≥ 0.05HGB is highly confident the infrastructure looks malicious, and the URL string isn't trivially clean.
in_high_op_guardop_p > 0.60 AND url_p < 0.05HGB confident, URL string very clean — almost certainly a legitimate platform deployment.
shortener_masktrue iff URL was identified as a known shortener apex (see fusion_kit/shorteners)Domain reputation of the shortener itself is uninformative; the resolved target carries the signal.

6.2 Zone blends (current zones, 4c8b112)

ZoneConditionBlendRationale
CDN-phishingin_cdndeploy_p = 0.65 · url_p + 0.35 · op_pWhen the operational model has no signal (truly clean infrastructure), url_p must dominate. CDN-fronted phishing is the canonical case.
Normal0.01 ≤ op_p ≤ 0.60deploy_p = 0.60 · url_p + 0.40 · op_purl_p carries a moderate advantage because the char-LR model is well-calibrated on phishing-keyword paths regardless of hosting reputation.
High-operationalin_high_opdeploy_p = 0.25 · url_p + 0.75 · op_pWhen DNS, WHOIS, TLS, content, ASN all line up against the URL, op_p should dominate; the URL string alone can't out-vote that much infrastructure evidence.
High-op low-url_p guardin_high_op_guardFall back to the normal blend.Legitimate platform deployments on vercel.app / pages.dev / replit.app land at url_p ≈ 0.001 - 0.026; without the guard they were misclassified as phishing purely on op_p. Real phishing in the high-op zone has url_p ≥ 0.06 (numeric domains, brand hooks in the path), so the guard does not suppress true positives.
Shortener overrideshortener_mask AND url_p ≤ 0.95deploy_p = 0.10 · url_p + 0.90 · op_pThe shortener itself is a layer of indirection; the resolved target is what matters. op_p over the resolved infrastructure dominates.
Shortener-self-suspicious exceptionshortener_mask AND url_p > 0.95Keep the normal blend.If the char-LR model is > 95% confident the shortener domain itself is malicious, do not suppress that signal — the shortener domain may be the phishing primitive.

6.3 Removed zones (do not document as present)

Established-domain zone — removed in aa5dafd. The original PR included a zone that damped phishing on CDN infrastructure by over-weighting op_p when url_p > 0.95 AND op_p ∈ [0.01, 0.10). The OpenPhish 2026-05-18 benchmark (§9) attributed ~80 extra false negatives per run to this zone. It was removed. Do not document it as still present in derived materials.

8.2 TI / L2 gate

In both the handler and the worker, L2 fires when:

!tiResult.Matched || tiResult.RiskScore < 80

i.e. the L2 sidecar is consulted unless TI already returned a high-confidence phishing verdict. This re-invites L2 on low-confidence TI hits so that the sidecar can either confirm or downgrade them.

8.3 Fail-open semantics

SVC-03 starts even if the sidecar is unreachable. Per-request: if the sidecar errors, the handler logs and continues without an L2 contribution — the L1 + TI verdict stands and the ml_* envelope fields are omitted. Per-startup: no pool.MustNew-style hard dependency on the sidecar; the detector binds lazily.

10. Design Justifications

DecisionRationale
d=1 typosquat (not d≥2)Against 10,000 reference apex domains, d=1 produces a manageable false-positive rate (~10−4 incident frequency in our sample). d=2 increases the collision rate roughly an order of magnitude — legitimate short brands like "go" / "io" / "ai" start matching unrelated apex domains. Latency also degrades quadratically.
Asymmetric weighting in fusionEach model has a distinct error mode: url_p miscalls small-business banking domains that look phishy-keyword-heavy; op_p miscalls CDN-hosted phish where the infrastructure looks clean. The four zones plus the high-op guard let each model dominate where it is reliable and back off where it is not. The matching docstring in scoring.py spells the rationale out per zone.
L2 re-invited on RiskScore < 80Low-confidence TI hits would otherwise either be force-classified phishing (FP risk) or dropped entirely (FN risk). Re-inviting L2 means a noisy TI hit becomes a hint, not a verdict, and the fusion math gets to confirm or reject.
Out-of-process Python sidecarThe HGB stack pulls in numpy + scipy + scikit-learn (~150 MB). Embedding that in every Go binary that needs phishing scoring is wasteful and a deployment headache. A single sidecar per node, called over HTTP, keeps the Go images slim and allows the model to be reloaded without restarting svc-03.
Char-LR over BERT-style URL modelsBERT-tier URL classifiers have higher AUC on academic benchmarks but require GPU inference for < 100 ms latency. Char-LR runs in microseconds on CPU and is sufficient when paired with op_p; the fusion math is what closes the accuracy gap.
Full-URL cache key (post-PR-#140 fix)The original PR keyed the LRU cache on apex domain, which collapsed distinct paths to one entry. Real phishing URLs share a phishing apex with benign control paths (/about, /contact) — one verdict for the apex was wrong for every URL but one. Full-URL keying is path-aware and the TTL is short enough (5 min) to keep memory bounded.

11. Limitations

# Limitation Impact Mitigation
1 brandSubstrings is hand-curated (20 entries) Coverage gap on regional brands and emerging unicorns. New phishing targets land before the guard knows about them. Rotate the list quarterly against APWG / OECD brand-abuse reports. A larger, generated list is feasible but risks FPs from substring collisions.
2 Cache is best-effort — no negative caching of errors A flapping enrichment dependency can cause the same URL to be re-scored on every hit. Acceptable today — 5-min TTL bounds the damage. If the sidecar becomes a hot loop, add short negative-TTL entries (~30 s) for transient errors.
3 SSRF guard is best-effort at the L7 boundary safeDialContext rejects non-public IPs at TCP connect time, but a service in front of svc-03 can still be tricked by DNS rebinding (TTL=0 records that flip between public and private addresses between the guard check and the actual fetch). Document the boundary as "trusted by the calling service". A robust fix requires pinning the resolved IP and bypassing the system resolver for the actual fetch — out of scope for the current PR.
4 Sidecar wasn't in CI before this round Regressions in serve.py or fusion math weren't caught by automation. Resolved by the new make e2e-svc-03 target (stubbed sidecar; runs in CI) and the opt-in make integration-svc-03 (real sidecar with the LFS-tracked bundles).
5 Ephemeral-platform suffix list is duplicated _EPHEMERAL_PLATFORM_SUFFIXES (Python, operational.py) and ephemeralPlatformSuffixes (Go, enricher/features.go) are maintained by hand. Drift would mean /score-features and /score disagree on the same URL. Either generate one from the other at build time, or pull both from a shared data file (e.g. JSON). Out of scope for this PR; flagged for the next refactor.
6 /score-features Go wiring (resolved) internal/phishing/client/client.go exposes ScoreFeaturesBatch/CachedScoreFeatures and internal/phishing/detector.go routes through /score-features whenever the Go enricher is loaded, saving the per-request HTTP / DNS / WHOIS round-trips inside the sidecar; it falls back to /score otherwise. No action — the "Go enricher computes features, sidecar just scores" optimization is now on the live request path.
7 Live-benchmark DR (100% on fresh OpenPhish, §9.2) is measured on one snapshot (n=286 scored) Single-run sample. DR on diverse corpora ranges 74.7%–100% depending on corpus (subtle phishing vs. active phishing kit). Confidence interval on any single corpus is wide. Rerun on rolling 7-day OpenPhish dumps; track DR trend over time. The 74.7% on LegitPhish subtle phishing is the honest lower bound for production-like traffic.
